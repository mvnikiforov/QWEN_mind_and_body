# Design

## Context

Целевой узел — блок строки ключевых слов в hero (`src/components/Hero.tsx:264-273`), уже приведённый к одной строке на мобильных предыдущей доработкой (capability `hero-keywords`):

```tsx
<div className="fadeup mt-9 border-y border-line py-4" style={{ animationDelay: "280ms" }}>
  <p className="flex flex-wrap items-baseline gap-y-1 font-display text-[clamp(16px,2.2vw,24px)] font-semibold uppercase tracking-[0.16em] text-ink/90 lg:text-[clamp(17px,2.2vw,24px)] lg:tracking-[0.22em]">
    {["Тело", "Чувства", "Разум", "Дух"].map((w, i) => (
      <span key={w} className="flex items-baseline">
        {i > 0 && <span className="mx-2 text-[0.55em] leading-none text-ink/35 lg:mx-4">•</span>}
        {w}
      </span>
    ))}
  </p>
</div>
```

Что важно для подхода:

- Абзац уже является flex-контейнером (`flex flex-wrap`) без `justify-content`, то есть по умолчанию `flex-start`. Центрирование по горизонтали — это ровно одно свойство на этом узле.
- Блок-обёртка не имеет ширины: он блочный, поэтому по умолчанию занимает всю ширину родителя (колонки `lg:col-span-7` на десктопе, полная ширина контента на мобильных). Линейки `border-y` рисуются по границам блока, то есть **по ширине колонки, а не по ширине текста** — центрирование абзаца их не затронет.
- Поля секции заданы контейнером `px-5 sm:px-8` (`Hero.tsx:211`); на 390px контентная область — 350px, на `sm`+ и на десктопе — ширина колонки.
- Измеренные факты предыдущей доработки (headless Chrome, сборка из текущей ветки): на 390px ширина текста 308.34px при 350px доступных, то есть свободно ~41.7px — 20.8px на каждый край. На 360px свободно 11.66px (5.8px на край), на 320px строка переносится.
- Существующие требования capability `hero-keywords`, которые правка обязана сохранить: одна строка на 390px, кегль/трекинг/поля разделителей не ниже текущих значений, десктоп без изменений, перенос ниже 390px без горизонтального выхода, разделитель в одной группе со словом, отсутствие изменений в структуре hero.

Спецификация поведения — `specs/hero-keywords/spec.md`.

## Goals / Non-Goals

**Goals:**
- Центрировать текст строки по горизонтали на ширинах < `lg`, сохранив линейки во всю ширину колонки.
- Не сдвинуть ни одного значения типографики, установленного предыдущей доработкой.
- Оставить десктоп выровненным по левому краю.

**Non-Goals:**
- Изменение кегля, трекинга, полей разделителей, высоты строки и вертикальных отступов блока.
- Сужение блока по ширине текста («плашка» с короткими линейками) и удаление `border-y` — решено пользователем как нежелательное.
- Центрирование соседних абзацев hero, кнопки «Выбрать формат» и статистики — они остаются по левому краю.
- Изменение `hero-layout` (верхний зазор) и `hero-visual` (круговой визуал).

## Decisions

### 1. Центрирование задаётся на абзаце, а не на блоке-обёртке
**Решение**: центрирование задаётся на абзаце, а не на блоке-обёртке: мобильное центрирование добавляется классом `max-lg:justify-center`, на `lg` выравнивание не переопределяется, потому что оно задаётся только для мобильных.

**Обоснование**: абзац — единственный узел, содержимое которого центрируется; блок-обёртка задаёт ширину и рисует линейки, и трогать её не нужно. Это автоматически выполняет требование «Rules keep spanning the content width»: ширина блока не зависит от ширины текста, потому что он блочный, а не inline.

**Альтернативы**:
- `mx-auto` + `w-fit` на абзаце и `text-center` — отклонено: `w-fit` сжимает абзац, а вместе с ним (при `border` на обёртке) потребовалось бы двигать и блок; лишние узлы и риск для линеек.
- `text-center` вместо `justify-center` — отклонено: `text-align` не влияет на flex-элементы, строка осталась бы прижата влево.
- Центрировать через `place-self`/`justify-self` — отклонено: абзац не является грид- или флекс-элементом, свойство не применится.

### 2. Мобильное центрирование через `max-lg:`-вариант, без `lg:`-переопределения
**Решение**: центрирование задаётся классом `max-lg:justify-center`; на `lg` и шире не применяется ничего, поэтому остаётся `flex-start` по умолчанию.

**Обоснование**: `max-lg:`-вариант ограничивает правило медиазапросом «уже `lg`», то есть ровно тем диапазоном, который объявлен в спецификации (мобильные — меньше `lg`, десктоп — `lg` и шире). На десктопе класс не выдаёт вообще ничего, поэтому поведение там не может «случайно» измениться.

Важная поправка к первоначальному решению: базовый `justify-center` действует на **всех** ширинах, а не только на мобильных. Проверено на сборке: с базовым классом `computed justify-content` равнялся `center` и на 1024px, и на 1440px, а замер отступа слева от текста давал 20.58px на 1024px и 82.22px на 1440px вместо 0. Это нарушало требования «Desktop stays left aligned» и «Desktop appearance unchanged» (сценарии спецификации), поэтому базовый вариант отклонён.

**Альтернативы**:
- Базовый `justify-center` без варианта — отклонено по факту замеров: задевает десктоп (см. выше).
- `justify-center lg:justify-start` — отклонено: по поведению равноценно выбранному, но требует явного класса там, где можно обойтись одним вариантом; выбранное решение не добавляет на десктопе ни одного правила.

### 3. Отступы разделителей при центрировании не трогаются
**Решение**: `mx-2 lg:mx-4` у точек и трекинг `0.16em` остаются как есть.

**Обоснование**: свободных 41.7px на 390px хватает, чтобы строка осталась в одну строку; центрирование лишь перераспределяет уже существующие поля внутри блока, не меняя суммарную ширину текста. Требование «Centring does not change the typography» выполняется буквально.

**Альтернативы**:
- Увеличить поля разделителей, «раздув» строку симметрично — отклонено: на 360px это потребовало бы либо уменьшения кегля, либо переноса; кегль и разрядка уже подобраны предыдущей доработкой.

### 4. Перенос ниже 390px остаётся и тоже центрируется
**Решение**: `flex-wrap` сохраняется, каждая строка переноса центрируется автоматически тем же `justify-center`.

**Обоснование**: свойство центрирует каждую строку флек-контейнера, поэтому отдельного правила для переноса не требуется. Структура «разделитель внутри span-а со своим словом» не меняется, поэтому требование «Each separator stays attached to its word» продолжает выполняться: при переносе вторая строка имеет вид «• ДУХ», а не «•» и «ДУХ» раздельно.

**Альтернативы**:
- На узких экранах возвращать выравнивание по левому краю (например, через дополнительный breakpoint) — отклонено: визуальный скачок выравнивания при повороте экрана; требование «Centring holds across the mobile range» запрещает разное поведение внутри диапазона.

### 5. Комментарий над блоком дополняется, а не переписывается
**Решение**: к существующему комментарию (`:253-263`) добавляется одна строка про центрирование на мобильных.

**Обоснование**: комментарий уже описывает мобильные типографические значения и их восстановление через `lg:`; выравнивание — часть той же мобильной/десктопной пары, поэтому оно принадлежит тому же комментарию. Переписывание потеряло бы обоснование предыдущей доработки.

## Risks / Trade-offs

- **[Риск: центрирование ломает «ровную левую колонку» hero на мобильных]** → Принято осознанно по решению пользователя: строка центрирована, соседние абзацы и кнопка остаются по левому краю, поэтому смещение строки читается как осознанный акцент, а не как сбой. Проверяется снимком на 390px (задача 3.2).
- **[Компромисс: на 360px остаётся всего ~5.8px поля с каждой стороны]** → Приемлемо: строка всё ещё читается как отцентрованная, а требование однострочности выполняется. При дальнейшем сужении экрана перенос сохраняет читаемость.
- **[Риск: `justify-center` влияет и на перенос строк при `flex-wrap`] → Желаемое поведение (см. решение 4), отдельно проверяется на 320px (задача 3.3).
- **[Риск: правка задевает `align-items`/базовую линию]** → Не задевает: добавляется только `justify-content`; `items-baseline` остаётся, поэтому вертикальное выравнивание слов и точек внутри строки прежнее. Проверяется замером высоты строки (задача 3.4).
- **[Риск: затрагивается строка с тем же текстом в футере]** → Футер — отдельный узел с собственными классами (`Footer.tsx:15-17`), правка его не касается. Проверяется снимком футера (задача 4.2).

## Migration Plan

Изменение типографическое, без миграции данных и API. Откат — удаление одного класса `max-lg:justify-center` из абзаца; обратная совместимость полная, так как значение по умолчанию `flex-start` восстанавливается автоматически.

## Open Questions

Нет: все решения, влияющие на спецификацию, приняты (центрируется только текст, линейки во всю ширину, область действия — мобильные).
